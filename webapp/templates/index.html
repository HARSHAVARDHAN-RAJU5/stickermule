How it works

A customer uploads a picture and orders a sticker at a size. The agent answers one question: will this print badly?

  1. Open the file. Check it really is an image, by its contents rather than its name. Turn it into a grid of pixels.
  2. Measure. How many pixels across? Where does the design sit? Is the background see-through or solid? How much fine detail is there, and where? Measurements only, no opinions.
  3. Compare each measurement to a rule. 288 pixels across a 3 inch sticker is 96 dots per inch. Printing wants 300. That fails. Every rule is a small, separate piece of code, and the numbers it compares against live in one settings file.
  4. Decide where the job goes. Anything failed, tell the customer. Something the agent cannot judge, send it to a person. Otherwise approve.

The six rules it currently applies

Resolution
Pixels divided by the ordered inches. Under 150 always fails. Between 150 and 300 the artwork decides: small lettering fails, a single large shape passes.
Missing transparency
A die-cut sticker needs a see-through background. A fully solid file cannot be cut to shape.
Fake transparency
The file has a see-through edge, but a white box is still sitting behind the design. It will print as a box.
Safe zone
How close the design comes to the cut line, when the background can be separated from it.
Picture of a sticker
The file is a screenshot of a finished sticker rather than the artwork for one: a white die-cut rim and a drop shadow already drawn in. Printed as-is, the customer gets a fake rim and a photograph of a shadow. A person decides, because a designer may have drawn a white outline on purpose.
Detail at the cut
Whether fine detail such as lettering runs off the edge. Flat colour running off the edge is deliberate and allowed; lettering is not. This one needs no background, so it works on full-bleed designs. On a photograph running to all four edges there is no background to find, so the agent treats the file as continuous-tone imagery and lets it through — full bleed is the point of it.

Writing to the customer

When a file goes back to the customer, a language model words the message. It never sees the picture, only short sentences the checks wrote, with the numbers already in them. Then a plain piece of code, the guard, reads the message and refuses it if it:

  • writes a number the checks did not measure,
  • leaves out a problem that was found,
  • brings up a problem that was not found,
  • promises anything, like a refund or an approval.

A refused message goes back to the model once, with the reasons. If the second one is refused too, or the model cannot be reached, the customer gets a fixed, pre-written message instead. Either way they only hear what the checks found.

What it will not do

No language model can change a verdict, add a finding, or approve a file. The route is decided before the model is asked anything.

It will not offer to sharpen a blurry file either. Enlarging pixels cannot invent detail that was never there, and doing it would look helpful while sending a soft print to press.
