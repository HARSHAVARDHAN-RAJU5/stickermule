# Artwork Pre-flight Agent

An agent that inspects a customer's uploaded design against the product they
ordered, decides deterministically whether it can be printed, and routes the
job. Custom printing runs on artwork that arrives wrong in a small number of
predictable ways; catching those before a human proofs the file is worth doing
well.

**Deterministic checks decide. A language model only explains.** Every verdict
comes from a pure function over pixel measurements compared against a threshold
in a config file. No model output can change a verdict, add a finding, or
approve a file.

> Independent prototype. Not affiliated with, and not a description of, any
> printing company's internal systems. All test artwork is generated by the
> code in `evalkit/art.py`.

## Run it

```
pip install -r requirements.txt
python -m preflight artwork.png --size 3x3 --shape die_cut
```

```
logo.png -> NEEDS_CUSTOMER_FIX  (214 ms)
  failing checks: ALPHA_FAKE
  [pass] RES_DPI        300 DPI at the ordered size
  [pass] ALPHA_MISSING  transparent background present (17.0% of pixels)
  [FAIL] ALPHA_FAKE     opaque region fills 100% of its bounding box and is a
                        uniform light colour; the background looks like a white
                        box, not a cut-out
```

`--json` prints the full findings. `--log runs/today.jsonl` writes the audit
trail. The exit code is 0 when approved, 1 otherwise, so it composes in a shell.

## Checks

Thresholds live in `config/thresholds.yaml`, never in the check bodies, so the
agent can be tightened without a deploy.

| Code | Measures | Fail | Warn |
|---|---|---|---|
| `RES_DPI` | `min(px_w / in_w, px_h / in_h)` | < 150 dpi | < 300 dpi |
| `ALPHA_MISSING` | transparent pixels, die-cut orders only | < 1% | — |
| `ALPHA_FAKE` | content filling its own bounding box, uniform and light | ≥ 97% | — |
| `SAFE_ZONE` | closest approach of content to the cut line | < 1/16 in | < 1/8 in |
| `DETAIL_AT_CUT` | closest approach of *fine detail* to the cut line | < 1/16 in | < 1/8 in |
| `STICKER_MOCKUP` | a white rim **and** a drop shadow already drawn in | — | always |

`RES_DPI` does not warn blindly in the middle band. Between 150 and 300 dpi the
artwork decides: a file full of small lettering fails, a single large smooth
shape passes. 200 dpi on a photograph prints fine; 200 dpi on 6 pt type does not.

`DETAIL_AT_CUT` measures the *density* of detail near the cut, not edges. Flat
colour running off the edge is deliberate — that is what full bleed is — and a
hard boundary between two flat colours scores 0.067, below the 0.10 threshold.
Small lettering scores 0.178. Because it needs no background separation, it
works on full-bleed files the safe-zone check cannot measure at all.

Seven more are specified but not built: `ASPECT`, `BLEED`, `ALPHA_HALO`,
`STROKE_MIN`, `CONTRAST`, `CUT_RADIUS`, `FONT_EMBED`, `INK_LIMIT`.

### What the eval found, in order

Each run that scored badly is here, with what was actually wrong.

**Run 1 — 94% route accuracy, 2 unsafe approvals.**

| | Run 1 | Now |
|---|---:|---:|
| Route accuracy | 94% | 100% |
| Approved when it should have been sent back | 2 | 0 |
| Files needing a human | 5 | 2 |

- **`fake_gradient_box` slipped through.** `ALPHA_FAKE` compared four corner
  samples, and a background ramping from 255 to 225 grey is not uniform corner
  to corner, so the check cleared it. It is still a white box and still prints
  as one. It now measures median lightness, chroma and spread across the whole
  perimeter band — a better model of what a background is, not a looser
  threshold.
- **`bleed_flat` was approved on a measurement that never happened.** Ink to all
  four corners leaves the flood fill nothing to flood, so no content was found
  and every geometric check quietly had nothing to say.

**The second fix was wrong the first time.** It was a `BACKGROUND_UNKNOWN`
warning that sent those files to a person. That removed the silent approval but
solved nothing: separating the background was never the goal. The goal is to
know whether something important is about to be cut off, and that can be
measured directly. `DETAIL_AT_CUT` replaced it, and full-bleed files are now
approved on their merits rather than escalated.

**Two more gaps, found by deliberately testing awkward files.**

- **A photo of a finished sticker was approved.** A 400 dpi product-page
  screenshot — white die-cut rim and drop shadow already in the image — passed
  every check. Sharp, well clear of the cut, no transparency problem for a
  square order. Printed, the customer gets a fake white border and a photograph
  of a shadow. `STICKER_MOCKUP` now looks for the two together: a nearly-white
  rim on the design's own edge (ordinary designs measure 27–186, mockups
  253–255) and a backdrop darker right around the design than further out
  (ordinary designs −2.3 to 1.1, mockups 3.5 to 8.6). It warns rather than
  fails, because a designer may have drawn that outline on purpose.
- **Ordinary full-bleed photographs were rejected.** Texture to the edges reads
  as lettering at the cut, so both geometric checks failed a completely normal
  order. The fix is a gate, not a looser threshold: is the background one
  connected region or scattered noise? Every ordinary design scores 100%; a
  photograph scores 66%. Below 95% `SAFE_ZONE` declines rather than measuring
  against speckle, and `DETAIL_AT_CUT` treats the file as continuous-tone
  imagery where reaching the edge is the point.

**Three labels were wrong, not the code.** A solid block bleeding off an edge is
not fine detail; a block corner 0.117 in inside a rounded die is genuinely
borderline; a coloured background *is* separable, so the geometric check does
run on it. Each correction is defensible on its own, but correcting labels
against output is how a test set quietly stops testing anything, so all three
are named in `docs/results.md`.

## Routing

- any `FAIL` → `NEEDS_CUSTOMER_FIX`
- only `WARN`s, all in the auto-approvable set → `APPROVED` with notes
- any `WARN` outside that set, or a check that raised → `HUMAN_REVIEW`
- all `PASS` → `APPROVED`

The auto-approvable set is one list in `config/thresholds.yaml`. It is the
single lever an operations lead owns.

A check that raises becomes a `CHECK_ERROR` finding, which is deliberately not
auto-approvable: a broken check sends the job to a human instead of quietly
approving it.

## Known limits

- **No real artwork has been tested.** Every file in the evaluation set is
  generated by `evalkit/art.py`. Real uploads are antialiased, gradient-filled
  and JPEG-compressed. A probe at JPEG quality 45 showed content detection
  holding to within 15 pixels, but safe-zone clearance drifting about 0.007 in
  downward on hard edges from compression ringing — toward false alarms rather
  than misses, which is the safer direction, but it means the clearance figure
  is softer than three decimals suggest.
- **Raster only.** PDF and SVG uploads are refused with a clear message rather
  than half-handled.
- **Lettering inside a full-bleed photograph is not caught.** When the
  background cannot be separated at all, the file is treated as continuous-tone
  imagery and detail at the edge is accepted as the picture itself. That is
  what stops ordinary full-bleed photographs being rejected, and the cost is
  that a caption running off the edge of a photograph slips through.
- **`STICKER_MOCKUP` cannot read intent.** A designer who draws a white outline
  and a soft shadow on purpose gets the same warning as someone who uploaded a
  product-page screenshot. That is why it escalates instead of failing.
- **The cut path is derived, not supplied.** For die-cut orders it is the
  content silhouette offset outward by 0.08 in, so safe-zone clearance is
  guaranteed by construction and the check is skipped. A customer-supplied die
  line would make it meaningful.
- **No colour management.** No ICC conversion, no press-accurate CMYK.
- **Thresholds are researched defaults**, not a production spec. A real printer
  would tune every one against their own equipment and remake data.

## Layout

```
preflight/
  types.py       Canvas, ProductSpec, Finding, Verdict, State
  config.py      thresholds loaded from YAML
  eventlog.py    append-only JSONL audit trail
  normalize.py   01 - magic-byte sniffing, EXIF, RGBA
  analyze.py     02 - features every check shares
  checks/        03 - one pure function per check
  decide.py      04 - findings -> one of three routes
  pipeline.py    the state machine
config/thresholds.yaml
evalkit/
  art.py         synthetic artwork primitives
  dataset.py     the 39 labelled cases and their ground truth
  harness.py     runs the set, scores precision/recall and the route matrix
  report.py      renders the markdown, caveats included
docs/results.md  generated
tests/
```
